# 공간·초대·월드 분리 구현

2026-09-21. 기존 SSO 로그인 뒤 공간 홈으로 이동하는 흐름을 추가했다. 일정 없이 T07~T09의 실행 가능한 첫 범위를 구현한다.

## 제공 기능

- 공개 탐색, 내 공간, 현재 목록 검색, 최근 방문순 정렬, 빈 상태·오류·재시도.
- 공간 생성: 이름 1~60자, 소개 최대 300자, PUBLIC/UNLISTED/PRIVATE, 정원 1~100명. 계정당 생성 20개.
- 소유자의 이름·소개·공개 범위 수정. 신규 공간은 GDG 오피스·캠퍼스 광장·스터디 라운지·밋업 홀 템플릿을 고를 수 있고, 월드 상태는 공간마다 별도다.
- PUBLIC/UNLISTED 공간의 선택형 입장 승인. 비멤버는 입장 요청을 보내고 소유자가 승인하면 멤버십을 얻는다. 기존 멤버와 유효한 초대 수락은 승인 절차를 건너뛴다.
- OWNER/ADMIN/MEMBER 역할. OWNER는 공간 설정과 역할 위임을 담당하고, ADMIN은 맵·초대·일반 멤버와 요청을 관리한다. 비공개 공간은 멤버만 조회/입장 가능하며 외부 사용자에게는 404를 반환한다. 링크 공개 공간은 목록에서 숨기고 로그인한 사용자가 공간 링크로 입장한다.
- 소유자의 초대 발급·목록·취소. 1~168시간, 1~100명 제한. 유효한 초대는 공간당 20개, 목록은 최근 50개다. 선택적으로 HUFS 계정 ID를 지정할 수 있고 이 초대는 해당 계정만 한 번 수락한다. 원문 코드는 생성 시에만 표시한다.
- 코드/링크 수락, 로그인 전 초대 링크를 열었을 때 탭 단위 복귀. 초대 링크는 URL fragment를 사용하고 바로 주소에서 제거한다. 로그인 뒤 사용자가 수락 버튼을 눌러 참가한다.
- 선택한 공간의 입장 준비에서 닉네임/아바타 저장, 실제 월드 연결, 공간 이름/정원 표시, 공간 홈으로 퇴장.

공개/링크 공개 공간에 최초 입장권을 요청하면 MEMBER가 된다. 공간을 비공개로 바꾸거나 초대 코드를 취소해도 기존 멤버는 유지된다. 설정·초대 UI에 이 동작을 안내한다. 공개 범위 변경은 기존 멤버 강퇴 기능이 아니다.

## 저장과 동시성

Flyway V4에 `town_space`, `space_member`, `space_invite`를 추가했다. 기본 공개 캠퍼스는 `00000000-0000-4000-8000-000000000001`이며 시스템 공간으로 소유자 편집 기능을 제공하지 않는다. 원본 에셋과 기존 계정 데이터는 그대로 사용한다.

초대 코드는 SecureRandom 128비트, Base64URL 22자이며 SHA-256 해시만 DB에 저장한다. 교환은 공간 행 → 초대 행 순서로 잠근 한 트랜잭션에서 멤버십과 사용 횟수를 갱신한다. 마지막 한 자리를 동시에 수락해도 하나만 성공한다. 기존 멤버의 중복 요청은 사용 횟수를 늘리지 않는다. 만료·취소된 초대는 기존 멤버도 재교환할 수 없지만 이미 보유한 공간 권한은 유지된다.

Flyway V41은 `space_invite.target_user_id`와 계정 외래 키를 추가한다. 계정 지정 초대는 최대 사용 횟수를 1로 고정하고, 대상이 아닌 계정은 멤버 여부와 관계없이 일반적인 사용할 수 없는 초대 응답을 받는다. 대상 ID와 표시 이름은 OWNER/ADMIN의 초대 목록에서만 보여주며, 사용자는 프로필에서 자신의 초대용 계정 ID를 복사할 수 있다. 계정 삭제 시에는 대상 지정 초대도 함께 제거된다. V47은 초대 발급 계정을 `created_by_user_id`로 저장하며, 발급 계정 탈퇴 뒤에도 초대 자체는 유지하고 발급자 참조만 비운다.

로그인한 사용자는 공간 홈의 받은 초대 보관함에서 자신의 계정으로 온 유효한 초대를 확인하고 수락하거나 거절할 수 있다. 받은 목록은 대상 계정에만 노출하며, 초대한 계정·공간 소유자·만료 시각을 보여준다. 만료·취소·소진된 초대, 이미 참여한 공간, 보관된 공간은 감춘다. 수락은 기존 코드 교환과 같은 공간→초대 잠금 순서를 사용하고 도메인 제한을 다시 확인한다. 멤버십·대기 중 가입 요청·초대 사용 횟수를 한 트랜잭션에서 갱신하며, 수락 재시도는 만료나 취소 이후에도 사용 횟수를 늘리지 않는다. 거절은 해당 대상의 초대만 취소한다. 기존 V41 초대 행을 재사용하고 V47로 발급 계정을 기록한다.

공간 변경/초대/입장권 발급은 CSRF와 로그인 세션, 활성 계정을 확인한다. 쓰기 요청은 계정당 분당 60회로 제한한다. 초대 코드를 GET URL이나 로그에 기록하지 않는다. API 계약은 `contracts/openapi.yaml`에 있다.

## 월드 입장과 경계

1. API `/spaces/{id}/admission`이 계정·공간 권한을 확인한다.
2. Redis에 30초의 일회성 256비트 입장권을 저장한다. 값은 사용자 ID·HTTP 세션 ID·공간 ID·정원에 바인딩된다.
3. 웹은 WebSocket 프로토콜 헤더에 `hufs-town-v2`, `hufs-ticket.<ticket>`을 보낸다. 서버는 고정 프로토콜 `hufs-town-v2`만 선택한다. 티켓을 URL/쿼리/로그에 넣지 않는다.
4. 월드는 Origin·쿠키 세션을 검증하고 Redis Lua로 동일 사용자/세션의 티켓만 원자적으로 소비한다. 다른 세션의 실패 요청은 정당한 티켓을 소모하지 않는다.
5. Redis Lua가 공간 단위 좌석을 원자적으로 선점한다. 월드는 입장 성공 뒤 actor 외부에서 20초 lease를 갱신하고, 재접속 토큰은 사용자·HTTP 세션에 바인딩해 기존 좌석을 재사용한다. 좌석 누락이나 Redis 오류는 fail-closed로 해당 접속을 종료한다.
6. 매 재접속은 새 입장권을 요청한다. 나가기/StrictMode 재실행 중 뒤늦게 도착한 응답은 세대 번호로 무시한다. 로그아웃·세션 만료 시 기존 주기 검사가 모든 해당 소켓을 닫는다.

## 현재 경계와 다음 태스크

- 공간 단위 Redis 정원은 맵·API 인스턴스에 걸쳐 원자적으로 예약되며, 별도 lease로 실제 참가와 15초 재접속 자리를 유지한다. Testcontainers에서 160개의 동시 입장 요청 중 정원 100개만 승인되는 것을 검증했다. 월드 actor 전체 상한 300명, 소켓 상한 320개는 과부하 제한이며 100명 실제 접속 성능 검증 결과를 뜻하지 않는다.
- T09.1 좌석 정원 lease는 완료했고 T10.3에서 참가자 소유권 lease/fence, 공간 라우팅, 안전 스폰, AOI snapshot과 월드 지표까지 구현·검증했다. Redis가 노드별 fence 번호를 발급하며 살아 있는 다른 노드가 같은 재접속 참가자를 복원하지 못하게 한다. lease 만료 뒤 소유권이 넘어가면 이전 노드는 actor tick에서 참가자를 제거하고 오래된 fence의 갱신·반환 요청도 거부한다. 패키징 월드 두 프로세스 통합 테스트에서 중복 입장 거부, fence 증가 후 복구, 이전 노드 퇴장을 확인했다. API는 `TOWN_WORLD_ENDPOINTS` 주소 목록으로 공간 ID를 rendezvous hash 라우팅하며 목록이 비어 있으면 같은 출처 월드 경로를 사용한다. 주소는 브라우저에서 접근 가능한 `ws://` 또는 `wss://` URL이어야 한다. 실제 actor tick/WebSocket 프로토콜 테스트에서 AOI 이탈 제거를 확인했고, `/actuator/metrics`에 tick·queue·참가자·소켓 지표를 노출한다. 100명/미디어 부하와 배포 중 노드 drain은 T26.1·T26.2에 남아 있다.
- 같은 브라우저 로그인 세션에서 같은 공간에 새 탭으로 입장하면 기존 좌석·아바타·복원 토큰을 넘겨받고 이전 소켓을 종료한다. 별도 로그인 세션은 별도 좌석을 사용한다. 지도/포털 이동은 참가자 ID를 유지하며 비정상 종료 좌석은 복구 유예 뒤 회수한다(T09.3).
- 홈의 둘러보기·내 공간·즐겨찾기 탭은 서버에서 검색하고 12개 단위로 페이지네이션한다. 결과 수와 이전/다음 상태를 응답한다. `browse`에는 공개 공간, 내가 참여한 공간, 입장 요청 중인 공간과 저장한 링크 공개 공간이 포함된다. 비공개 비멤버와 차단된 공간은 제외한다. 즐겨찾기와 최근 방문 동작은 [구현 기록](14-space-favorites.md)을 따른다.
- V19에서 공간 소유자의 멤버 목록·강퇴·입장 차단과 차단 해제를 추가했다. 강퇴는 멤버십 삭제와 `space_access_block` 기록을 한 트랜잭션으로 처리한다. 공간 목록/조회/입장 API는 제한된 계정을 거부하고, 유효한 초대를 다시 수락하면 차단을 해제하면서 멤버십을 복구한다.
- V20에서 PUBLIC/UNLISTED 공간에 `approval_required`와 계정별 입장 요청을 추가했다. 요청은 공간당 계정별 하나만 유지하고 재요청은 거절 상태를 대기 중으로 되돌린다. 소유자의 승인과 멤버십 부여는 하나의 트랜잭션이다. 거절·승인된 요청은 소유자 대기 목록에서 빠지며, 초대 수락 또는 직접 입장으로 대기 요청이 남지 않도록 정리한다.
- 승인제 공개 공간은 목록에 보이고, 승인제 링크 공개 공간은 링크로 열어 요청한 뒤 요청이 대기 중인 동안 목록에도 표시한다. 공간 홈은 대기 요청 상태를 10초 간격으로 새로고침하며 승인되면 입장 버튼으로 바뀐다. 정원은 admission 시점에 다시 검사되며 승인 자체가 좌석을 예약하지는 않는다.
- 활성 월드는 계정+공간 쌍의 권한을 500ms 간격으로 묶어 조회하고, 제한된 사용자의 해당 공간 세션과 재접속 토큰만 제거한다. 월드 권한 조회는 실패 시 fail-closed다. 영속 공간 채팅도 저장 직전에 멤버십과 차단 상태를 다시 확인한다.
- 멤버 목록, 입장 요청, 초대, 맵 편집과 제한 관리는 OWNER 또는 ADMIN이 할 수 있다. 역할 지정과 공간 설정은 OWNER만 가능하다. ADMIN은 OWNER/ADMIN을 강퇴할 수 없고 OWNER 역할도 변경할 수 없다. 차단 해제는 입장 거부만 해제하며 멤버십을 자동으로 만들지 않는다. 공개/링크 공개 공간은 이후 입장 요청으로 참여하고, 비공개 공간은 초대가 필요하다.
- V28에서 OWNER가 현재 멤버에게 7일 유효한 소유권 이전 요청을 보낼 수 있다. 대상자는 로비에서 수락·거절하고, 수락 트랜잭션은 `town_space.owner_id`와 양측의 OWNER/ADMIN 역할을 함께 바꾼다. 이전 소유자는 ADMIN으로 남으며 요청 취소·만료·대상 퇴장 시 정리한다. Testcontainers의 MariaDB/Redis 통합 검사에서 두 계정 요청·거절·취소·수락과 역할 변경을 검증했다. 로컬 Docker DB에는 V41까지 적용됐다. 실제 HUFS SSO 계정 왕복은 T06.2 검증에 남아 있다.
- V43은 SSO userinfo에서 받은 이메일의 정규화된 도메인을 HTTP session에만 두고 공간별 허용 목록으로 외부 계정의 검색·상세·요청·입장을 제한한다. 이 속성은 사용자 프로필/DB에 보관하지 않는다. 기존 멤버는 이후 이메일 도메인이 바뀌어도 권한을 유지하며, 초대 수락과 예정 행사 조회도 같은 정책을 따른다. V44 공개 공간에는 선택형 게스트 진입을 추가했다. 게스트는 30분 세션, 30초 일회성 세션 바인딩 티켓, 기본 지도만 사용하고 DB 계정·멤버십·관리 권한을 받지 않는다. 도메인/게스트 경계 기록은 [공간 접근 정책](17-space-access-policy.md)을 따른다.
- 공간 복제와 보관은 [공간 복제](19-space-cloning.md), [공간 보관](18-space-archiving.md) 기록에 구현했다. 영구 삭제와 실제 HUFS SSO 다중 계정 권한 왕복은 남아 있다. 계정 지정 초대는 V41, 도메인 정책은 V43, 게스트 설정은 V44로 구현했다. 소유권 이전 등 실제 SSO 브라우저 왕복도 별도 검수한다.
- 음성·화상·화면공유·근거리 미디어·맵 편집은 구현되어 있다. 실기기/모바일·다중 월드 게시 ACK·100명 미디어 부하 등 운영 검증은 T20, T25, T26을 따른다.

## 검증

Java 통합 검사는 폐기 가능한 MariaDB/Redis와 실제 world bootJar 별도 프로세스를 사용한다. 외부 SSO 전송만 mock한다. 공개/비공개/목록 비노출, 소유자 검사, 비활성 계정, 마지막 초대 동시 수락·중복 수락·취소·만료, 공간 간 snapshot 분리, 정원 초과, 공간을 바꾼 재접속 거부, 원래 공간의 재접속, 입장권 세션 바인딩·일회성·TTL을 검사한다.

소유권 이전 통합 검사는 비멤버를 대상으로 지정할 수 없고 MEMBER는 이전을 요청할 수 없는 것을 확인한다. 수락 전에는 기존 소유자가 OWNER로 유지되며, 대상 계정만 이전을 거절하거나 수락할 수 있다. 소유자 취소 뒤에는 대상 응답이 거절되고, 수락하면 `owner_id`와 양측 역할이 함께 바뀐다. 추가 통합 검사는 ADMIN이 멤버 관리·초대는 할 수 있지만 공간 설정, 역할 변경, 다른 ADMIN 강퇴는 할 수 없도록 확인한다. ADMIN의 일반 멤버 강퇴는 차단을 기록해 재입장을 거부하며, 차단 해제 후에는 재입장을 허용한다. 실제 로그인 계정 둘의 UI 및 월드 권한 갱신 확인은 아직 필요하다.

Playwright `tests/e2e/spaces.spec.ts`는 받은 이전 요청을 로비에 표시하고, 확인 대화상자 뒤 수락 요청·대기함 갱신·소유권 완료 안내가 나오는지 검사한다. 이 검사는 API를 모의하므로 별도 SSO 계정의 실제 권한 사용 검증을 대체하지 않는다.

프론트 단위 검사는 입장권 요청 중 나가기, StrictMode의 오래된 응답, 재접속 때 새 입장권 발급, 입장 거부 후 무한 재시도 방지를 검사한다. 브라우저 E2E는 실제 preview 월드와 UI용 API fixture를 이용해 로그인/프로필, 공간 생성/설정/초대/만료 오류, 모바일 초대 복귀를 검사한다. API fixture 결과를 실제 다중 계정 SSO 초대 완료로 표현하지 않는다.

검증 결과: Java 단위 14개, 실제 MariaDB/Redis·패키지 world 통합 11개, 웹 단위 8개, Chromium E2E 8개 통과. 타입 검사·프론트 빌드·bootJar·11개 공용 계약 생성물 일치·OpenAPI YAML 구문 검사 통과. Phaser의 기존 500KB 초과 청크 경고는 남아 있으며 실패는 아니다. 로컬 DB V4 적용과 기존 SSO 계정의 공간 홈 표시도 확인했다.

검사 중 브라우저가 요청한 WebSocket 프로토콜을 서버가 선택하지 않아 연결되지 않는 문제를 발견했다. 고정된 프로토콜을 명시적으로 선택하도록 수정했다. 아바타 파츠 필수 필드 추가에 맞춰 v2로 올렸다. InnoDB의 기본 반복 읽기에서도 동시 중복 수락이 기존 멤버를 놓치지 않도록 멤버십·초대 한도 조회에 현재 버전의 잠금 읽기를 사용한다. 동일 계정의 동시 수락 2건 모두 성공하고 사용 횟수는 1인 것도 검증했다.

실행 명령:

```powershell
./scripts/gradle.ps1 test :modules:persistence:integrationTest :apps:api:integrationTest :apps:api:bootJar :apps:world:bootJar
./scripts/e2e.ps1 -SkipBuild
# 프론트
pnpm contracts:check
pnpm test
pnpm build
```

`scripts/e2e.ps1`은 별도 임시 loopback 포트의 API·월드·Vite를 숨겨진 프로세스로 시작하고 테스트 후 자신이 만든 프로세스만 정리한다. 기존 5173의 SSO 서버와 로그인 세션을 변경하지 않는다.

최종 로컬 확인: 새 API/world jar로 재시작한 뒤 두 health가 UP이고 웹은 localhost:5173에서 실행 중이다. 기존 실제 SSO 계정을 유지한 브라우저에서 공간 홈 → 기본 캠퍼스 입장 준비 → 입장권 발급 → 월드 `연결됨 1 / 100` → 나가기 → 공간 홈 복귀를 확인했다. 사용자에게는 새 공간 홈을 열어두었다.

### 공간 멤버 강퇴·입장 회수 (V19)

소유자 멤버 관리 화면에서 MEMBER 계정을 내보내면 멤버십 행을 삭제하고 영구 입장 차단을 저장한다. 소유자 계정은 강퇴 대상으로 선택할 수 없다. 현재 월드 연결은 권한 묶음 조회에서 회수되고, 다른 공간의 세션에는 영향을 주지 않는다. 차단된 계정은 공간 탐색·상세·입장권 발급에서 거부되며, 소유자가 발급한 유효 초대를 수락하면 해당 공간의 차단이 풀리고 다시 멤버가 된다. 초대를 재사용할 수 없는 경우 소유자가 제한 목록에서 차단을 해제할 수 있다.

소유자 화면에는 멤버 이름, 참여일·최근 방문일과 제한된 계정 목록을 표시한다. UUID는 요청 식별에만 쓰며 화면에 출력하지 않는다. 강퇴와 제한 해제는 CSRF·소유자 권한·기존 쓰기 속도 제한을 따른다. 월드 권한 저장 조회가 실패하면 인증된 공간 세션을 유지하지 않는다. API/world bootJar, React production build, 생성 계약 검사(45개 레코드·타입)를 통과했다. 로컬 DB가 V19로 올라갔고 API·월드 health UP, 웹 200, 두 관리 목록의 비로그인 요청 401을 확인했다. 자동화 테스트와 실제 두 SSO 계정 간 강퇴·재입장은 실행하지 않았다.

### 입장 승인과 대기 요청 (V20)

소유자는 PUBLIC/UNLISTED 공간 설정에서 승인제를 켜고 끌 수 있다. 승인제 공간의 비멤버가 카드를 누르면 월드 입장 대신 입장 요청을 보낸다. 공간 홈은 요청을 기다리는 동안 상태를 10초마다 갱신하고, 승인 후에는 멤버로 표시해 정상 입장을 제공한다. 소유자의 멤버 관리 화면에는 요청자 이름·요청 시각과 승인/거절 동작이 표시된다.

API는 승인제 공간의 비멤버 admission을 서버에서 거부한다. 초대 링크 수락, 기존 멤버는 승인 없이 입장하며, PRIVATE 공간은 초대 정책을 그대로 쓴다. 요청 재전송은 계정당 멱등이고 거절된 요청은 다시 신청할 수 있다. 승인 트랜잭션은 요청을 잠그고 활성 계정을 확인한 뒤 멤버십과 결정을 함께 저장한다. 승인 후 admission에서 실제 공간 정원을 검사하며 좌석은 예약되지 않는다. 설정을 끄면 대기 요청을 정리하고, 초대/직접 입장으로 멤버가 된 계정의 오래된 대기도 승인 완료 상태로 정리한다.

API/world bootJar, 프론트 타입 검사·production build, 생성 계약 45개 검사를 통과했다. Prettier가 OpenAPI YAML을 읽고 포맷했으며, 로컬 DB가 V20으로 올라갔다. API·월드 health UP, 웹 200, 비로그인 대기 목록 401과 비로그인 요청 제출 차단 403을 확인했다. 자동 테스트와 다중 계정 승인·거절 브라우저 흐름은 실행하지 않았다.

### 공간 관리자 위임 (V21)

공간 소유자는 기존 멤버를 ADMIN으로 지정하거나 MEMBER로 되돌릴 수 있다. ADMIN은 맵 편집과 게시, 초대·입장 승인 요청·일반 멤버 강퇴 및 입장 제한 관리를 할 수 있다. 공간 설정과 역할 변경은 소유자에게 남기고, ADMIN은 소유자나 다른 관리자를 내보낼 수 없다. ADMIN을 강퇴하려면 먼저 소유자가 MEMBER로 역할을 낮춰야 한다.

V21은 `space_member.manager`를 추가하고 OWNER/MEMBER 저장 구조는 유지한다. API는 응답에서 이를 ADMIN 역할로 표현하고, 월드는 기존 공간 멤버십으로 인정한다. API/world bootJar, 프론트 타입·production build, 생성 계약 검사와 OpenAPI 파싱을 통과했다. 로컬 DB에 V21을 적용했고 API·월드 health UP, 웹 200을 확인했다. 자동 테스트와 실제 별도 SSO 계정의 권한 행사는 실행하지 않았다.

### 계정 지정 초대 보관함

공간 홈은 현재 계정으로 도착한 활성 초대를 불러와 공간 이름·소유자·만료 시각과 수락/거절 버튼을 보여준다. 목록은 브라우저 복귀 때와 15초 간격으로 갱신되고, 새로고침·재시도 상태를 제공한다. 수락 뒤 공간은 내 공간 목록으로 바뀌고, 거절 뒤 초대는 보관함에서 제거된다.

`SsoIntegrationTest.invitationLimitsAreAtomicIdempotentRevocableAndExpiring`의 확장 시나리오는 다른 계정의 조회·수락·거절 차단, ADMIN이 만든 초대의 발급자/소유자 구분, 대상 계정 수락과 사용 횟수 1회 유지, 초대 만료 뒤 수락 재시도, 거절에 따른 코드 폐기를 확인한다. `invite-flow.spec.ts`의 Playwright 두 시나리오는 초대 코드 진입과 계정 초대함 수락/거절 UI를 확인한다. 프론트 Vitest 48개, 타입 검사, production build, Prettier, OpenAPI Java/TypeScript 계약 74종 검사가 통과했다. Testcontainers에서 V47 적용을 확인했고, 로컬 API 컨테이너 로그는 V46→V47 마이그레이션 완료를 확인한다. API health UP, Tailnet UI 200, 비로그인 초대 보관함 API 401을 확인했다. Playwright의 계정 초대 API는 목 처리했으며 실제 HUFS SSO 두 계정의 브라우저 초대 수락/거절 검수는 아직 하지 않았다.

### 입장 승인 요청함 단일 조회 (2026-09-29)

로비는 이전에 내 공간 목록의 모든 페이지를 불러온 뒤 승인제 관리 공간마다 별도 요청을 보내 승인 요청함을 구성했다. 이제 `GET /api/v1/spaces/join-requests/incoming`을 사용해 서버가 소유자/관리자 권한과 승인제·보관 여부를 확인한 한 번의 조회 결과를 표시한다. 승인 요청이 많은 공간을 관리해도 네트워크 요청 수가 공간 수에 따라 늘지 않으며, 권한이 바뀐 공간 한 곳의 조회 실패가 다른 공간 요청을 숨기지 않는다. 프론트 타입 검사와 프로덕션 빌드가 통과했고 자동 테스트는 요청에 따라 실행하지 않았다. 실제 SSO 계정 승인 왕복은 남아 있다([운영 증거](evidence/26-admission-inbox-single-query-production-2026-09-29.json)).
