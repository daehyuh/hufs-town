# 회의 녹화

녹화는 로그인한 참가자만 이용할 수 있는 비공개 회의실 기능이다. 호스트가 녹화할 미디어 소스를 고르면 World 서버가 현재 회의실 참가자와 플레이어·미디어 epoch를 고정해 동의 요청을 만든다. 마이크·카메라·화면·화면 오디오는 각각 별도로 선택하며, 동의가 필요한 사람 모두가 허용하기 전에는 미디어 서버에 녹화 세션을 만들지 않는다.

한 명이라도 거절하면 시작하지 않는다. 참가자의 철회, 회의실 명단이나 미디어 권한 변경, 퇴장·맵 이동, 호스트 종료, 회의실 종료, 1시간 제한, 저장 용량 한도, 녹화 서버 종료는 녹화를 끝낸다. 참가자 동의와 서버 상태는 회의실 참가자에게 WebSocket으로 전파한다. 화면에는 소스와 30일 보존 기간, 현재 동의/녹화 상태를 표시한다.

World 서버는 내부 bearer 인증 제어 API를 통해 선택된 회의실의 허용 소스 RTP producer만 미디어 서버에 전달한다. 미디어 서버는 producer별 PlainTransport consumer로 RTP를 받아 각 트랙을 WebM 파일로 저장한다. 트랙마다 소스·epoch·상태·파일 크기·SHA-256·수신 RTP 패킷/바이트를 manifest에 기록하고, 종료된 파일의 최대 보존 만료를 30일로 둔다. 파일은 전용 Docker volume에 저장되며 클라이언트가 직접 지정할 수 있는 미디어 RPC나 공개 파일 응답 경로는 없다. 저장 실패나 빈 파일은 완료 상태로 취급하지 않고 내부 운영 로그에 기록한다.

## 검증

`WorldRecordingTest`는 호스트 권한, 전원 동의 전 미디어 요청 차단, 거절·철회, 참가자 변경 취소를 확인한다. 미디어 Node 검사에서는 도메인·epoch·source 권한과 파일 정리 정책을 검사하고, 합성 RTP 입력이 실제 재생 가능한 WebM으로 저장되는지 `ffprobe`로 확인한다.

추가 Chromium E2E는 실제 Docker mediasoup, Spring World, 프론트 UI를 연결해 두 참가자가 회의실에 입장하고 마이크 RTP를 송출하는 흐름을 사용한다. 첫 참가자 동의 뒤 파일이 생기지 않는 점, 둘째 참가자의 동의 뒤 녹화가 시작되는 점, 선택하지 않은 source가 기록되지 않는 점, 중지 후 파일 크기·해시·RTP 수신량 및 WebM 재생 시간을 확인한다. 이 검사는 실 HUFS SSO가 아니라 미리보기 서버에 기본 비활성화된 테스트 신원을 사용하므로 실제 IdP 로그인 검수는 T06.2에 남는다.

참가자가 완성된 녹화를 찾아 재생·다운로드·삭제하는 API와 UI, 녹화 사용량/한도 관리 화면은 T28.3 범위다. 음성 인식, 화자별 자막과 회의 기록은 T28.2에서 다룬다.

2026-09-26 보존·삭제 제어 기반: 미디어 서버의 bearer 인증 내부 control API에 완료된 녹화 목록과 삭제를 추가했다. 목록은 요청한 `worldId`와 비공개 회의실 `domain`이 일치하고 30일 보존 기한이 남은 파일만 반환하며, 실제 파일 크기를 합산하고 저장 경로와 참가자 ID는 응답에 포함하지 않는다. 삭제는 같은 공간 범위에서 종료된 녹화만 허용하고 활성 녹화는 거절하며, 성공하면 manifest와 WebM 파일이 든 디렉터리 전체를 지운다. 격리 Docker에서 미디어 테스트 28/28 통과(FFmpeg WebM 재생, 네이티브 worker 포함). 이 내부 API는 아직 사용자 인증 API/UI나 파일 재생·다운로드 경로가 아니며, 사용자별 접근 권한·전체 사용량 제한/알림은 T28.3의 남은 작업이다.

2026-09-26 메모리 수명주기 보강: 녹화 종료 시 세션을 활성 목록에서 제거하고 track map, participant/source 배열, World·peer 검증 함수·router 획득 함수 참조를 해제한다. 중복 종료 요청은 결과만 최대 128개 보관하는 고정 크기 캐시로 응답하며 녹화 삭제 시 해당 응답도 지운다. 시작 실패는 완료 결과 캐시에 남기지 않는다. 반복 종료 후 참조 해제와 캐시 상한을 확인하는 검사를 추가했고, 격리 Docker 전체 미디어 테스트 29/29 통과(FFmpeg 재생·mediasoup native worker 포함). 사용자 인증 녹화 목록/재생·다운로드 API/UI, 사용자 소유권 검증, 전체 사용량 제한과 알림은 여전히 T28.3에 남아 있다.

## 사용자 보관함과 파일 프록시

World는 녹화 시작 시 검증한 `spaceId`, `mapId`, 게시 map revision UUID, `zoneId`, 요청 계정 UUID와 참가자 계정 UUID를 내부 bearer API로 미디어 서버에 전달한다. 미디어 manifest는 이 값을 기록하고, 공간별 control 응답은 내부 player IDs·파일 키를 제외한 사용자 권한 확인용 메타데이터만 돌려준다. 완료·보존 중인 WebM만 반환한다.

Spring API의 `GET /api/v1/spaces/{spaceId}/recordings`, `GET .../{recordingId}/tracks/{trackId}/content`, `DELETE .../{recordingId}`는 세션 인증을 요구한다. 모든 요청에서 현재 공간 멤버십·차단 상태를 확인하고, OWNER/ADMIN은 해당 공간의 모든 녹화를 볼 수 있으며 일반 멤버는 녹화 참가자 목록에 계정이 있을 때만 읽을 수 있다. 삭제는 요청자 또는 OWNER/ADMIN만 가능하다. API는 신뢰된 미디어 manifest의 space ID와 URL의 space ID가 일치하는지 검사한 뒤 파일을 프록시하므로 브라우저에는 world ID, domain, participant UUID, 저장 경로, 해시나 내부 bearer 토큰을 보내지 않는다. WebM 트랙은 단일 byte range를 지원하고 206/416 상태와 검증된 Content-Range를 전달하며 `no-store`로 응답한다.

회의 녹화 패널의 보관함은 한국어·영어 목록, 회의실/소스/시작 시각/보존 만료/용량 표시, 오디오·영상 재생, 다운로드와 확인 절차가 있는 삭제를 제공한다. 재생 URL은 동일 출처 세션 쿠키를 사용하고 삭제 요청은 기존 CSRF API 클라이언트를 사용한다. API controller 단위 검사 5/5, 실제 Spring·Testcontainers 요청 통합 검사 1/1에서 세션 인증, CSRF 삭제, 참가자와 공간 운영자 권한, 비참가자 거부, 다른 공간으로의 파일 ID 교차 접근 차단, Range 부분 재생과 파일 삭제 제어 API 호출을 확인했다. Media 전체 검사는 격리 Docker 컨테이너에서 35/35 통과했고, 프론트 Vitest 83/83·typecheck·production build·Prettier가 통과했다. 기존 대형 번들 경고는 남아 있다.

보관함의 `usedBytes`는 현재 사용자가 열람할 수 있는 녹화만 합산한다. 아래의 공간별 녹화 한도와 관리자 저장량 경고를 추가했으며, 실 HUFS SSO 브라우저 검수는 남아 있어 T28.3은 미완료다.

2026-09-27 공간별 녹화 저장 한도: media 기본 공간 한도를 10GiB로 두고 `MEDIA_RECORDING_SPACE_MAX_BYTES`로 배포 설정에서 바꿀 수 있게 했다. 각 녹화의 최대 파일 크기를 보수적으로 예약한 뒤 공간별 lock 안에서 완료 파일, 기존 활성 녹화, 대기 중 예약을 함께 계산한다. 따라서 같은 공간의 서로 다른 비공개 방에서 동시에 요청해도 한도 내 예약만 통과한다. `list-space`는 전체 사용량과 한도를 관리자용으로 제공하고 Spring API는 OWNER/ADMIN에게만 전달한다. 일반 멤버는 기존처럼 본인이 볼 수 있는 항목과 그 합계만 받는다. 보관함은 항목이 없을 때도 전체 사용량을 표시하고 80% 이상에서 경고한다. 저장량이 부족하면 Media의 `RECORDING_SPACE_QUOTA` 오류가 World 녹화 상태에 안전한 실패 코드로 전달되어 안내 문구를 표시한다. media 동시 예약 테스트, Spring Controller/SSO 통합 검사, World Java 컴파일 및 프론트 관련 검사를 통해 동작을 검증했다. native mediasoup worker가 없는 현재 개발 환경에서는 네이티브 worker 검사와 실제 SSO 브라우저 검수는 확인하지 못해 T28.3은 미완료다.

## 동의형 AI 음성 자막

`MEDIA_TRANSCRIPTION_API_KEY`가 비어 있으면 전사 기능을 사용할 수 없고, 보관함 capability 응답도 이를 반영한다. 키를 서버 환경에 설정하면 회의 호스트가 녹화 요청에서 AI 음성 자막을 선택할 수 있다. 이 선택은 World 녹화 동의 상태에 포함되고, 모든 현재 참가자가 동의해야 녹화를 시작한다. 참가자에게는 마이크 오디오가 외부 음성 인식 서비스로 전송되며 AI 자막에 오인식이 있을 수 있다고 녹화 동의 전후로 알린다. 화면·카메라 트랙은 전사 API에 보내지 않는다.

전사는 녹화 중 진행하지 않는다. 동의된 녹화가 종료되고 마이크 WebM 트랙이 확정된 다음 비동기 큐에 넣어 녹화 종료 응답을 막지 않는다. 서버에서 트랙을 mono 16 kHz MP3로 변환하고 최대 22 MiB 업로드 한도를 적용한다. 각 트랙에 연결된 참가자 표시 이름과 녹화 내 오프셋을 이용해 발화 시각과 화자 이름을 조합하며, 외부 응답의 화자 ID는 계정 이름으로 신뢰하지 않는다. 대기·처리·완료·실패 상태를 manifest에 원자적으로 기록하고 서버 재시작, 제공자 오류, 변환 실패를 실패 상태로 남긴다. 완성된 자막은 8 MiB 제한과 30일 보존을 같은 녹화 디렉터리에 적용한다. 트랙 삭제·공간 삭제·만료 정리 때 진행 중 전사도 취소한다.

세션 인증 Spring API의 `GET /api/v1/spaces/{spaceId}/recordings/{recordingId}/transcript`는 현재 공간 멤버십과 참가자 또는 OWNER/ADMIN 권한을 다시 확인하고, Media 내부 transcript 경로를 bearer 인증으로 요청해 개인정보 캐시를 금지한 응답으로 전달한다. 보관함 UI는 처리 중 상태를 갱신하고 자막을 화자·시각과 함께 표시한다. 모든 화면에서 AI 생성 및 오인식 가능성 안내를 유지한다. Media 전사·녹화 검사 25/25, World `WorldRecordingTest`, API `SpaceRecordingArchiveControllerTest`, 프론트 Vitest 42개 파일·134개 테스트와 production build를 통과했다. 외부 제공자 키가 설정되지 않은 환경에서는 실 API 호출을 하지 않으며, 실 HUFS SSO 검수는 T28.3 운영 확인에 남아 있다.
