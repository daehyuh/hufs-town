# 함께 이동 요청

참가자 패널은 현재 맵 주변의 프로필 목록과 별도로, 같은 공간의 온라인 참가자 최대 100명을 보여 준다. 공간 목록에는 이름·외형 요약·상태·맵 이름만 있으며 위치 좌표나 계정 식별자는 포함하지 않는다. 다른 맵이나 현재 화면에서 멀리 있는 사람도 검색해 메시지를 보내거나 합류를 요청할 수 있다. 수신자가 승인하면 서버가 대상의 맵에서 안전한 빈 위치를 찾아 요청자를 근처로 이동시킨다. 수신자는 언제든 거절할 수 있다.

## 계약과 정책

- 클라이언트는 `joinRequest`를 보내고 서버는 수신자에게 `joinRequestEvent`, 발신자에게 `joinRequestAck`를 보낸다. 수신자의 `joinResponse` 후 발신자에게 `joinResult`를 전달한다.
- 발신자와 수신자가 모두 같은 공간에서 연결되어 있고 `AVAILABLE` 상태여야 한다. 차단 관계가 있거나 차단 정보를 확인하지 못한 경우 거절한다. 자기 자신, 오프라인 플레이어, 이동 장벽 중인 플레이어는 대상이 될 수 없다.
- 요청자는 5초마다 한 번 요청할 수 있고 한 번에 1건만 보류할 수 있다. 상대방에게 동시에 표시하는 요청은 최대 4건이다. 요청은 30초 후 만료된다.
- 대상이 PRIVATE 구역 안에 있으면 요청자도 같은 구역에 있을 때만 요청할 수 있다. 승인 시 서버가 같은 구역 안의 충돌 없는 위치를 탐색한다. 구역 밖으로 우회하거나 벽·다른 아바타와 겹치지 않는다.
- 미디어 통화 구역 경계를 넘어 합류할 때는 회수 장벽이 끝날 때까지 도착 좌표를 예약된 점유 위치로 취급한다. 여러 요청을 연속 승인해도 아직 좌표 적용 전인 참가자와 같은 위치를 고르지 않는다.
- 다른 맵의 대상에게도 같은 공간 안에서 요청할 수 있다. 대상이 승인하면 서버가 안전한 도착 좌표와 지도 ID를 결정하고, 클라이언트는 기존 resume token으로 해당 지도의 입장 티켓을 받아 재접속한다. 기존 공간 좌석을 재사용하므로 정원이 중복 예약되지 않는다. 도착 좌표는 서버 메모리에 30초간만 보관하고 목적 지도·충돌·PRIVATE 구역 안전성을 재검사한 뒤 적용한다.
- 대상이 PRIVATE 구역 안에 있으면 같은 구역 안의 요청자만 합류할 수 있다. 다른 맵에서 PRIVATE 구역 참가자를 찾은 경우는 거절한다.
- 수신자가 승인하기 전에는 위치가 바뀌지 않는다. 승인 순간에도 상태·접속·epoch·차단·구역을 다시 확인한다. 같은 맵에서 미디어 domain이 바뀌면 서버가 기존 연결 회수 장벽을 거친 뒤 좌표를 적용한다. 다른 맵 전환은 SFU 회수 응답 또는 2.2초 장벽 시간 만료 뒤에만 재접속 결과를 보낸다.

## 구현 위치

- 프로토콜 schema 및 생성 Java/TypeScript 레코드: `contracts/world.schema.json`, `scripts/generate-contracts.mjs` (`spaceParticipants`, `SpaceParticipant`)
- actor 전용 요청 보관·권한 재검사·빈 좌표 탐색·만료: `apps/world/src/main/java/town/hufs/world/WorldHandler.java`
- 공간 전체 온라인 목록 갱신·전파와 개인정보 최소 프로필: `apps/world/src/main/java/town/hufs/world/WorldHandler.java`
- 참가자 검색, 다른 위치 참가자 목록, 메시지/합류 버튼, 수신 승인/거절 카드, 결과 피드백: `../프론트/src/app/App.tsx`, `../프론트/src/game/WorldConnection.ts`, `../프론트/src/app/styles.css`

실시간 World 합류 요청은 같은 공간의 온라인 참가자에게만 가능하다. 오프라인 대상에게 요청을 남기거나 다른 공간에서 접속 중인 사용자와 약속하는 기능은 아래 계정 기반 비동기 요청함이 지원한다. 프로필 상세 카드와 개인 메시지는 기존 참가자 프로필 및 DM 기능을 사용한다.

## 오프라인·다른 공간 대상의 비동기 합류 요청

REST 기반 `GET/POST /api/v1/me/join-requests`, `GET /outgoing`, `POST /{requestId}/respond`, `POST /{requestId}/cancel`를 추가했다. 현재 World WebSocket에 없는 오프라인 계정이나 다른 공간에서 플레이 중인 계정도 요청함에 요청을 남길 수 있다. 요청자는 요청할 때 자신이 멤버인 만남 장소를 고르며, 그 공간 이름은 수신자에게 명시적으로 공유된다. 대상은 로비에서 승인 또는 거절할 수 있다. 요청은 7일 뒤 만료되며 발신자는 대기 요청 1건, 수신자는 대기 요청 4건까지만 보유한다. 발신 간격은 5초로 제한한다.

이 비동기 경로는 클라이언트가 상대 계정 ID를 보내지 않고, 이미 본인이 속한 1:1 DIRECT 대화의 opaque conversation ID를 보낸다. 서버는 DIRECT 종류와 요청자의 대화 멤버십을 확인한 뒤 정확히 한 명의 활성 상대를 결정한다. 그룹 대화나 다른 사용자의 대화 ID는 숨김 응답으로 거절하고 임의 계정 ID 입력은 받지 않는다. 요청자는 함께 멤버인 공간 중 하나를 목적지로 지정하며, 서버는 발신 계정의 현재 멤버십과 공간 보관 상태를 확인하고 공간 이름을 요청에 저장한다. 상호 차단 및 계정 상태를 요청 시점과 응답 시점에 검사한다. 목록에는 상대 표시 이름, 선택 메시지, 상태와 발신자가 공유한 목적 공간만 포함한다. 요청 대상의 현재 온라인 여부, 공간·맵, 좌표, 계정 ID는 반환하지 않는다.

수신자가 승인하면 요청은 최근 7일간 요청함에 남고 `공간 열기` 동작이 나타난다. 이를 누르면 현재 World를 닫고 SpaceLobby의 기존 입장 절차를 연다. 공개 공간은 기존 admission ticket을 받고, 승인제 공간은 기존 공간 입장 요청을 보내며, 비공개 공간은 이미 멤버이거나 관리자의 초대를 받아야 한다. 만남 승인은 멤버십이나 정원 좌석을 부여하지 않으며 공간 입장 정책을 우회하지 않는다.

Testcontainers 통합 검사에서는 대상이 오프라인인 경우와 다른 PRIVATE 공간 World WebSocket에 연결된 경우 각각 요청 생성·수신·승인을 확인했다. 오프라인 대상은 공개 목적 공간을 승인한 뒤 일반 admission ticket으로 실제 World welcome을 받았다. 비멤버가 비공개 목적 공간 요청을 승인해도 상세 조회와 `POST /admission`이 모두 404로 거부되는 것을 확인했다. 요청자가 속하지 않은 DIRECT 대화 ID는 404로 감추고, 요청 본문에 임의 사용자 ID를 넣는 방식은 400으로 거절한다. 목록에는 발신자가 선택한 공간 이름만 공유하고 대상의 현재 공간·맵·좌표·계정 ID는 노출하지 않는다. 프론트 People 요청함은 승인 후 `공간 열기`를 통해 SpaceLobby로 이동하고 기존 admission 절차를 거친다. Chromium E2E는 현재 공간을 다시 여는 동작이 재접속하지 않고 안내하는 것, 공개 공간 입장 티켓 요청, 승인제 공간의 기존 입장 요청 전송을 확인한다. 실제 HUFS SSO 계정 화면 왕복과 승인제 공간 관리자 승인 후 입장은 남아 있다.

자동화 검증(2026-09-24): Testcontainers MariaDB·Redis와 실제 패키징 월드에 두 개의 인증 세션을 연결해 합류 요청 ACK, 수신자 승인 카드 이벤트, 승인 응답 뒤에만 발생하는 이동 결과, 요청자가 대상 근처의 충돌 없는 위치에 도착하는 것을 확인했다. 테스트의 SSO 사용자 정보 응답은 목 처리하며 실제 계정 간 화면 확인은 남아 있다.

월드 정책 회귀(2026-09-25): `WorldIntegrationTest`에서 대상이 PRIVATE 회의실 안에 있을 때 외부 참가자의 요청을 `JOIN_PRIVATE`로 거부하고 대상에게 요청 알림을 보내지 않는지 확인했다. 같은 구역 참가자의 요청은 수신자가 명시적으로 거절할 수 있으며 `JOIN_DECLINED` 결과와 함께 요청자 좌표가 그대로 유지된다. 테스트는 실제 월드 snapshot에서 움직임 입력 ACK까지 대기해 위치를 비교한다. 승인 경로의 API/Testcontainers 검사와 함께 월드 통합 테스트가 통과했다.

동시 승인 좌표 예약(2026-09-25): 패키징 World 두 계정 통합 시나리오에서 두 요청자를 `SILENT` 구역으로 이동시키고 공개 구역 참가자가 요청을 연속 승인하도록 했다. 미디어 제어 서버의 revoke 응답을 보류한 동안 좌표가 확정되지 않은 경계 상태에서 모두 승인되며, 회수 완료 뒤 각각 다른 충돌 없는 좌표로 합류하는 것을 확인했다. 서버는 기존 위치뿐 아니라 미디어 barrier가 예약한 목적 위치도 점유 검사에 포함한다. Docker Testcontainers API 통합 검사가 통과했다.

다른 맵 합류와 좌석 재사용(2026-09-25): SSO 통합 환경에서 공개 지도와 스터디룸 지도를 각각 연결한 두 참가자 사이의 요청·승인을 확인했다. 테스트 SFU가 회수 응답을 보류하는 동안 `joinResult`가 전달되지 않고, 응답 해제 뒤 목적 지도 ID를 전달했다. 요청자가 같은 resume token으로 재접속하면 player ID와 epoch가 이어지며 Redis 공간 좌석 수는 2석으로 유지된다. 새 스냅샷에서 요청자는 대상과 겹치지 않는 0.5~4.1타일 거리의 안전한 좌표에 도착했다. `WorldHandler`는 승인 좌표를 30초짜리 서버 측 전환 예약으로 보관하므로 클라이언트가 임의 좌표를 요청할 수 없다. `:apps:api:integrationTest --tests ...approvedJoinAcrossMapsResumesTheSameSeatNearTheTarget`가 통과했다. 이 시점에는 오프라인 대상·다른 공간 합류와 실제 HUFS 계정 간 화면 확인이 남아 T16.3은 IMPLEMENTING 상태였다.

공간 참가자 검색과 실제 맵 이동 UI(2026-09-25): World는 같은 공간의 연결된 참가자 최대 100명을 맵 ID/이름, 이름, 아바타 외형 요약, 상태만 담은 `spaceParticipants` 메시지로 보낸다. 참가자 목록은 현재 시야 밖이나 다른 맵에 있는 사람도 검색하며, AVAILABLE 상태의 참가자에게 1:1 메시지 또는 합류 요청을 보낸다. 차단 목록도 같은 공간 범위로 계산해 다른 맵 참가자의 DM/합류 버튼을 일관되게 제한한다. `WorldIntegrationTest.publishesLiveParticipantProfilesAcrossMapsAndRemovesDisconnectedPlayers`가 두 맵 사이의 최초 명단, 프로필 변경 revision, 연결 종료 반영을 검사한다. `space-participants.spec.ts`는 두 브라우저로 다른 맵 참가자 검색→합류 요청→상대 승인→목적 맵 재접속을 확인했고 1/1 통과했다. 연결 단위 9/9, TypeScript 검사, 생성 계약 확인도 통과했다. 소개·링크는 전체 명단에 싣지 않고 원격 프로필 카드를 열 때 별도 `profileRequest`로 불러온다. 월드는 같은 공간 연결 여부와 차단 상태를 재검사하고 요청 속도를 제한하며, 권한이 없으면 상세 정보를 비워 보낸다. 월드 통합 및 SSO/Testcontainers 검사가 서로 다른 공간과 차단된 참가자의 상세 정보 차단을 확인했고, 두 브라우저 E2E가 프로필 표시와 합류 경로를 통과했다. 이 시점 이후 V49에서 오프라인·다른 공간 대상의 비동기 합류 요청이 추가됐다. HUFS 실계정 화면 왕복은 남는다.

비동기 만남 요청 프론트 연결(2026-09-25): People 패널에 받은 요청 승인·거절과 보낸 요청 취소, DIRECT DM 헤더에 대화 ID 기반 요청 보내기를 연결했다. 요청함은 outgoing 내역도 표시하며, 승인 뒤 자동 이동하지 않는다는 안내를 보여준다. 프론트는 상대 계정 ID를 표시하거나 요청 본문에 싣지 않는다. mocked Chromium E2E 1/1에서 승인·거절·취소와 `{ conversationId }` 전송을 확인했고, Vitest 15개 파일 51개 검사·TypeScript 검사·production build가 통과했다. 실제 HUFS SSO 두 계정 화면 왕복은 남아 있다.

다른 맵 합류 브라우저 회귀 보강(2026-09-28): Chromium E2E가 별도 지도 테스트 모드 없이 실행되어 두 참가자 모두 기본 맵에 들어가던 설정 오류를 발견했다. 프로필 창의 실제 동작 이름도 `합류`여서 오래된 선택자를 함께 수정했다. 테스트는 대상 승인 후 `destinationMapId=study-room` 결과와 요청자의 World 소켓이 해당 맵으로 다시 연결되는지 검사한다. E2E 실행 스크립트는 전체 브라우저 회귀 또는 이 테스트 파일을 실행할 때 다중 지도 미리보기를 자동 활성화한다. 기본 스크립트 호출로 이 Chromium 시나리오가 1/1 통과했고, 전 캠퍼스 브라우저 회귀도 12/12 통과했다. 프론트 Vitest 45개 파일·151개 검사, TypeScript, Prettier도 통과했다. 이는 로컬 미리보기 검증이며 실제 HUFS 인증 계정 간 운영 확인은 남아 있다.
