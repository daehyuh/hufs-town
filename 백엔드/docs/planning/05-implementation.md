# 05. AI 전체 구현 계획과 태스크 실행 규칙

## 1. 진행 원칙

**AI가 설계 보완, 프론트엔드, 백엔드, 월드, 미디어, 에디터, 테스트, 배포 설정, 운영 문서까지 처음부터 끝까지 구현한다.** 개발 기간, 작업 시간, 인력 투입량, 목표 출시일은 계획에 두지 않는다. 실행 순서는 선행 조건과 완료 기준으로만 결정한다.

계정 소유자의 인증, 비밀값 제공, 외부 서비스 권한, 기기 권한처럼 외부 입력이 필요한 항목은 해당 태스크의 입력 조건으로 기록한다. AI는 먼저 준비 가능한 코드·설정·검증 절차를 완성하고, 외부 입력이 없는 경우 그 조건에 의존하지 않는 태스크를 계속 진행한다. 미확인 연동을 완료로 표시하지 않는다.

한 번에 전체 기능을 생성하지 않는다. **실제로 완료 조건을 확인할 수 있는 수직 기능 하나**씩 구현하고, 계약·데이터 변경·UI·실제 서버 동작을 함께 끝낸다. 서버가 없는 임시 UI는 명확히 데모로 표시하며 완료로 세지 않는다.

기술 검증 → 서비스 기반 → 실시간 기능 → 편집·행사 → 통합 검증·배포 순서의 의존 관계를 따른다. G0~G8은 기능 묶음, R0/R1/R2는 완성 범위를 나타낸다. 날짜나 기간을 뜻하지 않는다. 사용자가 요구한 에셋 편집·독립 통화·전체 공유·달리기·찌르기는 R1 필수다.

실제 체크리스트의 기준 문서는 [08-task-backlog.md](08-task-backlog.md)다. 이 문서는 실행 규칙·태스크 간 관계·검증 기준을 정의한다.

구현 스택은 React/TypeScript/Phaser 웹, Java/Spring Boot API·Spring WebSocket 월드, MariaDB/JPA/Flyway, Redis를 기본으로 한다. Java/TypeScript 계약 호환, 월드 동기화 직접 구현, 세션별 송신 큐, 실제 MariaDB 통합 검증을 T01·T03·T10·T26에 포함한다. 미디어는 별도 SFU로 유지한다.

| G7 운영·출시 | 신고·역할·감사·백업·복구·접근성·부하 | 운영 가능한 정식 서비스 | 출시 체크와 모니터링·복구 훈련 완료 |
| G8 고도화 | 화이트보드, 예약, 녹화/자막, 게임, 연동 | 실제 사용자 요청 기반 확장 | 각 기능의 별도 동의·비용·회귀 검증 |

G0 미디어 엔진은 권한·구역 전환·트랙 회수·TURN 검증 결과로 선택한다. 후보 A가 필수 조건을 충족하면 채택하고, 충족하지 못하면 원인을 기록한 뒤 후보 B를 검증한다. 외부 설정 부재와 엔진 자체의 기능 미충족을 구분한다. 엔진 선택과 검증이 완료돼야 종속 미디어 구현 태스크를 완료할 수 있다.

R0는 G4 완료 시점이지만 비공개 테스트 참가자만 대상으로 한다. 공개 초대 시험 전에 최소 강퇴·차단·속도 제한·운영 연락 수단을 먼저 갖춘다.

작업 종료마다 08 문서의 체크 항목과 실행 기록을 함께 갱신한다. 별도 일정표나 중복 진척표를 만들지 않는다. ADR은 실제로 결정이 바뀔 때만 추가한다. 구현/검토 지적이 생기면 그것을 수정하고 관련 검사만 다시 실행한다. 단순한 문구 변경에 불필요한 테스트 묶음을 추가하지 않는다.

## 5. 검증 전략

### 정책 단위 검사

입장 정책, 초대 사용량/만료, 역할, 거리 edge, 비공개 구역, 차단, 포털, map schema, 원자적 게시 조건처럼 UI만으로 확인하기 어려운 규칙에 집중한다. 구현 코드와 같은 로직을 복사한 테스트 대신 입력과 기대 결과를 독립적인 표로 관리한다.

### 서버 통합 검사

JUnit·Testcontainers의 실제 MariaDB/Redis를 사용해 동시 정원 예약, 초대 중복 교환, draft version 충돌, lease 만료, 이벤트 재전송, 멤버십 취소, 자산 참조 보호를 확인한다. Flyway 마이그레이션, outbox 대상별 ACK/재시도, Java/TypeScript 계약 fixture, 맵 버전 포인터와 스냅샷이 어긋나는 실패를 포함한다. 위치 변경마다 JPA 트랜잭션이나 Redis 왕복을 수행하지 않는지도 확인한다.

### 브라우저 흐름

Playwright 여러 context로 생성자·멤버·외부인·운영자 흐름을 재현한다. 가짜 카메라/마이크는 UI 자동 검사에만 쓰며, 실제 소리·코덱·TURN·화면 오디오 품질이 확인된 것으로 세지 않는다.

최소 실제 장치 검증은 데스크톱 2대 + 모바일/다른 네트워크 1대를 권장한다. 이어폰으로 음향 피드백을 방지하고 사용자 A/B/C 역할을 분리한다. 학교·회사 Wi-Fi, 모바일 핫스팟, UDP 제한 환경의 TURN 경로를 확인한다.

### 부하 검증은 네 갈래

1. **월드만:** 25→50→100명 이동, 15분 준비·30분 측정. 지도 크기/오브젝트 수/수정 내역 고정.
2. **RTC만:** 12명 양방향, 100명 발표 수신, 100명 전체 모임 송출/선택 수신. 실제 인코딩/디코딩 또는 동등한 media sender/receiver를 사용.
3. **통합:** 100명 이동+채팅+근거리 그룹+화면공유+구역 이동을 60분 지속.
4. **장애:** 월드 재시작·미디어 제어 실패·네트워크 변경·DB 저장 실패·맵 게시 실패 후 복구.

WebSocket 봇 100개만으로 영상 100명 시험을 대체하지 않는다. 반대로 headless 브라우저 100개를 같은 기기에서 돌려 클라이언트 병목을 서버 한계로 오해하지 않는다. 부하 발생기 자원과 서버 자원을 따로 측정한다.

## 6. 출시 목표 수치

측정 기준: 서울/국내 사용자 중심, RTT 50ms 이하·패킷 손실 1% 이하 정상 네트워크, 1280×720 이상 지원 데스크톱에서 기록. 다른 환경은 별도 결과를 표기한다. 전 세계 모든 기기에 대한 보장이 아니다.

| 지표 | R1 목표 | 측정 방법 |
|---|---|---|
| 입장 성공률 | 유효 참가자 99% 이상 | 테스트 시도 결과, 정원 거부 등 정책 실패 제외 |
| 입장→월드 조작 | warm p95 3초, cold p95 8초 이내 | 번들·지도·인증 대기 구간별 계측 |
| 위치 전달 지연 | 원격 화면 반영 p95 150ms 이내 | 서버 tick·클라이언트 수신/렌더 계측 |
| 게임 성능 | 표준 노트북 50fps 이상 목표, 저사양 30fps | 지정 장치·맵·100명 상태 고정 |
| 일반 통화 연결 | 근접 안정 판정 후 p95 1.5초 이내 | policy→SFU→첫 재생 시간 |
| 정책 회수 | 요청→SFU 적용 p95 250ms 이내 목표 | 실제 전달/Consumer 상태, 버퍼 잔여 별도 |
| 비공개 전환 | 이전 경계 회수 확인 뒤 새 통화 허용 | 전체 전환 상태 및 트랙 검사 |
| 서버 tick | p95 처리 시간 25ms 미만 | 50ms tick 중 여유 확보 |
| 자원 안정성 | 60분 시험에서 연결·트랙·메모리 지속 누적 없음 | GC 이후 추세·객체 수·미디어 자원 |
| 기본 운영 가용성 | 월 99.5% 목표 | R1 운영 시작 후 실제 계측; 사전 실적 아님 |

목표 미달이면 영상 수/품질·업데이트 빈도·맵 한도·하드웨어를 조정하고 다시 측정한다. 100명 요구를 말없이 낮추지 않는다. 비공개 경계 실패는 수치 평균과 관계없이 출시 차단 항목이다.

## 7. 정식 출시 체크

- GDG HUFS SSO 로그인·로그아웃·재로그인·계정 탈퇴가 실제 운영 설정에서 동작한다.
- 공개/비공개/코드 초대·철회·차단·정원·중복 탭 규칙이 일치한다.
- 근거리·독립 회의실·전체 모임·발표의 전달 범위를 검증했다.
- 화면공유 종료·구역 이동·권한 변경 후 트랙이 남지 않는다.
- 맵 편집·게시·롤백·동시 저장 충돌·업로드 검증을 통과했다.
- 원본 에셋의 출처와 공개 배포 권한, 로고 활용 범위를 정리했다.
- 100명 월드/RTC/통합 시험의 조건·비용·결과를 남겼다.
- 운영자 기능, 사용 신고, 남용 속도 제한, 오류 연락 경로가 있다.
- 비밀값·로그·데이터 보존 정책, 개인정보 안내와 이용 규칙을 준비했다.
- 백업을 실제로 복원했고 배포 실패를 되돌리는 절차를 수행했다.
- 지원 브라우저와 모바일 제한을 UI/도움말에 표시했다.

법적 적합성 판단은 이 문서의 범위가 아니다. 공개 운영에 필요한 실제 정책·약관 문서는 배포 대상과 데이터 처리 방식이 확정된 시점에 별도 검토한다.

## 8. AI 태스크 실행 규칙

1. 08 문서에서 선행 마스터 태스크와 입력 조건을 충족한 미완료 태스크를 찾는다. 번호순보다 의존 관계를 우선한다.
2. 같은 마스터 안에서는 `.1 → .2 → .3` 순서로 구현한다. 앞 태스크의 검증 가능한 산출물을 다음 태스크가 사용한다.
3. 계약·마이그레이션·실제 기능·화면·오류 상태를 필요한 범위에서 함께 구현한다.
4. 완료 기준을 실행으로 확인하고 실패를 수정한다. 증거 없이 체크하지 않는다.
5. 코드/설정 경로와 실제 검증 결과를 실행 기록에 남긴다. 마스터는 세부 항목 모두 완료돼야 완료다.
6. 외부 입력이 필요한 경우 `BLOCKED`와 필요한 입력을 기록한다. 그 입력에 의존하지 않는 태스크는 계속 진행한다.
7. 선택 기술이 바뀌면 해당 태스크의 산출물·계약·ADR을 갱신한다. 시간 추정이나 마감일을 다시 만들지 않는다.

상태는 `TODO → IMPLEMENTING → VERIFYING → DONE`을 기본으로 하고, 외부 조건 때문에 진행할 수 없는 항목에만 `BLOCKED`를 사용한다. 실행 가능 여부는 선행 조건에서 계산한다. 코드가 생성됐어도 검증이 남아 있으면 `VERIFYING`이다.

T26은 T01~T25와 통합 완료 기준이 모두 충족된 뒤 완료할 수 있다. 제품 코드·실제 연동·배포 환경·운영 문서까지 확인한다. 문서 작성이나 로컬 데모만으로 제품 전체를 완료 처리하지 않는다.

## 10. R2 확장 태스크의 범위

T27~T32도 AI가 구현할 수 있는 태스크로 명세한다. R1 완료 후 선행 조건을 충족한 항목부터 진행할 수 있다. 선택형 수익화·마켓 기능은 기능 범위와 외부 서비스 입력이 정해진 뒤 활성화하며, 미활성 항목을 구현 완료로 표시하지 않는다.

제품 내 행사 날짜, 세션 만료, 지연 목표, 데이터 보존, 부하 시험 길이는 기능·검증 명세이므로 유지한다. 개발 일정이나 인력 기준 추정과는 별개다.
